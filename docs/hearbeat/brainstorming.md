# Tri-hand 비트 연출 프로젝트: 구현 계획

> 이 문서는 구현 계획 문서임. 영상/음원 내용은 이 단계에서 분석하지 않음.
> 이전 초안의 "평면 → 세움 → 움켜쥠" 서사와 에너지 기반 규칙은 폐기함.

## 1. 목표와 전제

**목표**: 스크립트를 실행하면 음원이 재생되고, 손이 정해진 모션을 **박자에만 맞춰** 수행한다.

**전제**
1. 영상(0:00~1:14)에서 **모션만 먼저 파악**해 5개 이하로 정의한다. (별도 작업, 윈도우 PC에서 진행)
2. 정의된 모션을 **음원의 비트 그리드 + 규칙 기반 시간표**로 실행한다. 영상은 실행 시 사용하지 않는다.
3. MuJoCo에서 먼저 검증하고, 같은 모션/시간표를 실물 로봇에 이식한다.
4. 음원·영상은 GitHub 저장소에 함께 올린다.
5. 로봇은 소리에 반응하지 않는다. 미리 계산한 비트 시각을 입력으로 받는 시간표 재생 방식이다.
6. 곡은 1개로 고정하며 확장성은 고려하지 않는다.

**하지 않는 것**: 영상 자동 포즈 추정, 실시간 오디오 반응, 1:14 이후 구간, 곡 교체 지원

## 2. 작업 분담과 인수인계 (핵심)

분석은 다른 컴퓨터(윈도우)에서 하고, 구현은 이 저장소에서 하므로 **둘을 잇는 파일 형식**을 먼저 고정한다.

```
[윈도우 PC: 영상 분석]            [이 저장소: 구현]
 영상 0:00~1:14 시청/분석   →     motions.json (모션 정의)   →   규칙 기반 시간표
                                  beats.json  (음원 분석)    →   실행(음원 + MuJoCo/실물)
```

- 영상 분석 담당자가 전달할 것은 **모션 정의 표 하나**(6장 형식). 코드/관절값까지 완성하지 않아도 되며, 동작 설명 + 박자 길이 + 대략적인 손가락 움직임이면 충분함
- 이 저장소에서는 그 표를 `motions.json`으로 옮기고 MuJoCo에서 관절값을 다듬음
- `beats.json`은 음원 분석을 **한 번 실행해 결과를 커밋**함. 실행 단계에서는 오디오 분석 라이브러리가 필요 없음
- 윈도우 PC에서는 파이썬/MuJoCo 환경이 없어도 됨 (표만 채우면 됨). 필요 시 `git pull`로 영상·음원만 받아 사용

## 3. 타이밍 기준 (135 BPM 가정, 분석에서 확정)

| 단위 | 길이 |
|---|---|
| 1박 (4분음표) | 약 444 ms |
| 8분음표 | 약 222 ms |
| 16분음표 | 약 111 ms |
| 1마디 (4박) | 약 1.78 s |
| 74 s | 약 41.6마디 (약 167박) |

- 1:14는 마디 경계가 아니므로, 시간표의 끝은 **1:14에 가장 가까운 마디 경계**로 하고 `beats.json`의 실제 비트 시각으로 확정
- 곡 앞의 무박자 인트로가 있으면 첫 다운비트 시각을 `beats.json`에 기록해 시간표의 t=0 기준으로 사용
- 영상과 mp3의 인트로 길이가 다를 수 있음. 모션은 **박 단위**로만 기술하므로 영상의 절대 시각은 구현에 쓰지 않음

## 4. 하드웨어 한계

| 항목 | 값 | 출처 |
|---|---|---|
| 관절 | A_j0(엄지 요, ±1.0472 rad), A_j1/j2, B_j1/j2, C_j1/j2 (7개) | `src/hand.xml` |
| 오므림 부호 | A: −, B·C: + | `run_sim.CLOSE_SIGN` |
| 안전 가동 범위 | j1: 0~0.3 rad, j2: 0~1.2 rad | `run_sim.Q_CLOSE` |
| 서보 | XL430-W250, 토크 1.4 N·m, 제어 입력 ±1.5708 rad | `AGENTS.md` |
| 속도 상한 | 3.0 rad/s | `teleop.MAX_SPEED` |

- 1박(444 ms): 큰 동작 가능 / 8분음표(222 ms): 중간 진폭 / 16분음표(111 ms): 미세 떨림 수준
- j1은 범위가 좁아 눈에 띄는 큰 동작은 **j2와 A_j0**가 담당할 가능성이 높음
- 모션 정의 시 "이 박 길이 안에 도달 가능한가"를 검사 (7장 검증 규칙)

## 5. 싱크 전략

- **도착 시점을 비트에 맞춤**: 비트 시각에 동작이 "끝나는" 쪽이 박자에 맞아 보임
- **마스터 클럭**: 음원 재생을 시작한 시각 `t0 = time.perf_counter()`을 기준으로, 모든 목표값을 `t - t0`의 함수로 계산 (누적 오차 방지)
- MuJoCo: 시뮬레이션 시간이 아니라 **실시간 페이싱**으로 스텝을 진행해 음원과 맞춤. 뷰어 없이 시간표만 검증할 때는 음원 없이 가상 시간으로 빠르게 실행
- 실물: Time-based Profile(Profile Velocity = 도착 시간 ms) + Sync Write로 손가락 간 시간차 제거. 마지막 몇 ms는 바쁜 대기
- 오디오 출력 지연은 고정 오프셋 상수 하나(`AUDIO_OFFSET`)로 두고 한 번 측정해 보정. 블루투스는 지연이 크니 유선 권장
- 고정 지연보다 지터가 문제. U2D2 레이턴시 타이머를 1 ms로 설정 (윈도우: COM 포트 속성)

## 6. 모션 정의 (영상 분석 결과를 채움)

한 모션 = "1박 또는 1마디 안에 끝나는 짧은 패턴". 사람 춤을 손가락 7자유도로 옮기는 것이므로 **동작의 리듬·강약만 가져오는 것**이 원칙.

| ID | 이름 | 영상 속 춤 동작 | 사용 손가락/관절 | 길이(박) | 강도(작게/보통/크게) |
|---|---|---|---|---|---|
| M1 | (미정) | | | | |
| M2 | (미정) | | | | |
| M3 | (미정) | | | | |
| M4 | (미정) | | | | |
| M5 | (미정) | | | | |

추가로 함께 기록하면 규칙 설계에 도움이 되는 것: 영상에서 각 모션이 **어느 구간(대략 몇 초~몇 초)에 쓰였는지**, 반복 횟수, 쉬는 박 위치.

## 7. 구현 계획

### 7.1 파일 구성 (제안)

```
src/heartbeat/
  beats.json         # 음원 분석 결과: bpm, 다운비트/비트 시각 (커밋)
  motions.json       # 모션 정의 (6장 → 관절값)
  schedule.py        # 규칙: (마디, 박) → 모션 ID. 시간표 생성
  choreo.py          # 순수 함수: choreo(t) → {관절: 목표각}. MuJoCo/실물 공용
  analyze_audio.py   # mp3 → beats.json (1회 실행, librosa 등. 실행에는 불필요)
  play.py            # 진입점: 음원 재생 + 시간표 실행 (--headless / --motors)
assets/ 또는 docs/hearbeat/   # Heartbeat.mp3, heartbeat.mp4
tests/test_heartbeat.py
```

- 기존 `run_sim.py`(`apply_ctrl`, `CLOSE_SIGN`, `Q_CLOSE`)와 `motors.py`를 **그대로 재사용**하고 중복 구현하지 않음
- 파일 위치(`src/heartbeat/` vs `src/` 직속)는 기존 `src/` 구조에 맞춰 구현 시 결정

### 7.2 데이터 형식

- `beats.json`: `{"bpm": ..., "first_downbeat": s, "beats": [s, ...], "end": s}`
- `motions.json`: 모션별 `duration_beats`와 키프레임 목록 `[{"beat": 0.0, "q": {"B_j2": 0.8, ...}, "ease": "..."}]`
  - 값은 관절 각도(rad) 대신 **0~1 정규화 오므림량**(0=펼침, 1=`Q_CLOSE`)으로 하면 부호 규칙이 한 곳(`CLOSE_SIGN`)에 모임. A_j0만 rad
  - 기술하지 않은 관절은 이전 자세 유지

### 7.3 규칙 기반 시간표

- 입력은 비트 그리드(마디/박 번호)와 모션 라이브러리뿐. 규칙은 코드로 두되 파라미터는 데이터로 분리
- 규칙 후보
  - 마디 범위별 사용 모션 풀 (구간 A: M1/M2, 구간 B: M2/M3 …)
  - 매 마디 첫 박 악센트(진폭 배율)
  - N마디마다 필 인(fill) 모션 삽입
  - 손가락별 지연 오프셋(i × 1/8박)으로 웨이브
  - 마지막 마디: 정지 자세 또는 마무리 모션
- **같은 입력이면 항상 같은 시간표** (난수 사용 시 고정 시드)

### 7.4 검증 규칙 (코드로 자동 검사)

1. 모든 관절 목표가 `safe_range` 안인가
2. 인접 키프레임 간 `|Δq| / Δt ≤ 속도 상한`인가 (박 길이 안에 도달 가능)
3. 모든 모션의 도착 시각이 비트(또는 8분음표) 그리드에 정렬되는가
4. 시간표가 `beats.json`의 끝(≈1:14)을 넘지 않는가

위반 시 어느 마디/모션인지 출력하고 실행 중단. 실물 이식 전 반드시 통과.

### 7.5 단계와 완료 기준

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 0 | 모션 정의 표 수령(6장) | 모션 5개 이하, 길이(박)와 강도 기재 |
| 1 | `analyze_audio.py` → `beats.json` | BPM, 첫 다운비트, 1:14 근처 마디 경계 확정 |
| 2 | `motions.json` + `choreo.py` + 검증 규칙 | 단위 테스트 통과, 헤드리스에서 마디별 목표값 로그 출력 |
| 3 | `schedule.py` 규칙 시간표 | 74초 시간표 생성, 검증 규칙 통과 |
| 4 | `play.py` 음원 + MuJoCo 뷰어 | 음원과 모션이 눈/귀로 맞음. `AUDIO_OFFSET` 보정 |
| 5 | 실물 백엔드(`motors.py` 연결) | 실물에서 MuJoCo와 같은 시간표 재생, 지연/지터 측정 |

단계 2~3까지는 헤드리스 + 테스트로 끝낼 수 있고(AGENTS.md의 헤드리스 기본 원칙), 4단계부터 GUI와 음원이 필요함.

## 8. 환경

- 음원 분석(1단계)은 어디서든 1회만 실행. 결과(`beats.json`)를 커밋
- 실행(4~5단계)은 **윈도우 네이티브 권장**: 음원 출력, GUI 뷰어, U2D2(COM 포트)가 모두 WSL2 없이 동작. 현재 브랜치 `feat/windows-real-motors`와 일치
- 오디오 재생 라이브러리는 mp3 디코딩 가능하고 윈도우/리눅스 모두 동작하는 것으로 선택 (예: `pygame.mixer`). 결정 후 `requirements.txt`에 추가
- `librosa` 등 분석용 의존성은 실행 의존성과 분리해서 기재
- 경로는 `pathlib` 기준으로 작성해 OS 의존을 없앰 (`run_sim.py`의 `Path(__file__)` 방식 유지)

## 9. 저장소 / 저작권

- 음원(약 3 MB)과 영상(약 36 MB)은 GitHub 단일 파일 한도(100 MB) 안이므로 LFS 없이 올릴 수 있음. 다만 영상은 50 MB 경고선에 가까우니 더 커지면 재인코딩
- 한 번 커밋하면 이력에 남아 지우기 어려우므로 **올리기 전에 위치(`docs/hearbeat/` 유지 여부)와 공개 범위를 확정**
- 공개 저장소에 상용 음원/영상을 올리면 저작권·삭제 요청 이슈 가능. 비공개 저장소이거나 사적 사용이면 문제가 적음
- 실행 코드는 음원 파일 경로를 상수 하나로 참조해 파일을 빼도 코드가 깨지지 않게 함
